# 음료 편집 드래그 성능

이 문서는 v1.1.0 이후 작업 중인 개선을 설명한다. GitHub 릴리즈 및 토스 실제 배포와는 별개다.

## 변경 이유

기존 음료 편집은 `pointermove`마다 목록 위치를 읽고 드래그 좌표를 React 상태로 전달했다. 따라서 미리보기만 이동할 때도 전체 카테고리와 배지를 다시 렌더링했다. 미리보기의 `top`과 `left` 변경도 레이아웃 작업을 늘렸다.

현재 구현은 다음처럼 역할을 나눈다.

- 입력 이벤트는 최신 좌표를 저장하고 한 번의 `requestAnimationFrame`을 예약한다.
- 프레임에서 최신 좌표로 위치를 판정하고 미리보기의 `translate3d`만 갱신한다. React 상태는 드래그 시작·종료와 배치가 달라질 때 갱신한다.
- 자동 스크롤 없이 손가락이 멈추면 프레임 예약과 위치 측정을 중단한다.
- 드롭은 프레임을 기다리지 않고 마지막 좌표로 즉시 판정해 편집 미리보기에 반영한다. 완료를 누를 때 편집 내용을 한 번에 저장하고, 저장 실패 시 미리보기를 유지해 다시 시도한다.

공통 훅을 사용하므로 같은 카테고리의 음료 순서, 다른 카테고리로 이동, 카테고리 순서 변경 모두에 적용된다. 기존 배지·카테고리 디자인과 저장 형식을 유지하며 의존성은 추가하지 않았다.

## 재현과 검증

`tests/catalog-drag-performance.spec.ts`는 드래그 시작 후 한 프레임 전에 터치 이동 100건을 전달한다. 실제 DOM 위치 조회를 계측하고, 이후 미리보기 위치와 마지막 드롭의 결과를 확인한 뒤 완료로 저장한다.

| 검사 | 이전 코드 | 개선 코드 |
| --- | --- | --- |
| 이동 100건을 전달하는 동안 동기적으로 실행한 목록 위치 조회 | 320회 | 0회 |
| 자동 스크롤 없이 정지한 8프레임의 목록 위치 조회 | 별도 기준 수치 없음 | 0회 |

0회는 입력 이벤트 안의 조회를 뜻한다. 실제 위치 판정은 예약된 프레임에서 수행한다. 이 결과를 기기의 FPS나 전체 드래그 연산이 0회라는 의미로 해석하지 않는다.

개선 코드는 375px·390px 모바일 화면, CPU 6배 지연, 브라우저 저장소 및 설치된 토스 SDK의 네이티브 브리지 모의 환경에서 검증했다. 브리지 모의 환경은 실제 휴대폰의 WKWebView·Android WebView 렌더러와 동일하지 않으므로, 실제 미니앱의 부드러움은 새 AIT 번들을 기기에서 확인해야 한다.

기존 `catalog-layout.spec.ts`와 `catalog-history-snapshots.spec.ts`는 빠른 드롭, 이동 이벤트 생략, 움직이는 카테고리 제목, 좌우 경계, 자동 스크롤, 취소·뒤로가기, 저장 실패·지연, 기존 기록 보존을 검증한다.
